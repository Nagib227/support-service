# Отчёт по практике

Тема: сервис обработки заявок на Java и Kotlin.

## Что сделано

Собран один сервис `support-service`. Java отвечает за заявки, статусы, историю, справочник и ошибки. Kotlin считает сводку и вызывается из Java-контроллера. Данные хранит PostgreSQL, схему накатывает Flyway. Проверки — JUnit, Mockito и Testcontainers. Запуск описан в Docker Compose, поставка — в GitHub Actions.

Аналитика: [specification.md](specification.md), [backlog.md](backlog.md). Контракт: [api.md](api.md). Проверки: [test-plan.md](test-plan.md), дефект D-1: [defects.md](defects.md).

## Два решения, на которые повлиял Kotlin

1. Среднее время имеет тип `Double?`. Для заявки `RESOLVED` длительность берётся через `closedAt?.let`: если времени закрытия нет, строка не попадает в расчёт и не вызывает ошибку. Пустой список длительностей остаётся `null`, а не нулём. В Java тот же смысл пришлось бы выражать отдельным флагом или `Optional` вокруг уже посчитанного числа.

2. Все показатели сводки считаются операциями над одной коллекцией: `count`, `associate`, `filter`, `mapNotNull`, `average`. Java-интерфейс `TicketReportQuery` один раз читает заявки периода `[from, to)` и отдаёт неизменяемые строки `TicketReportRow`. Kotlin не обращается к JPA. Так выполняется требование «одна выборка» и сохраняется граница: контроллер на Java вызывает Kotlin-сервис, а данные приходят через Java-интерфейс.

Отдельно Kotlin-тест `javaStatusPolicyRejectsReopenOfTerminalTickets` напрямую проверяет Java-класс `StatusTransitionPolicy`. Правила перехода не продублированы на втором языке: и карточка заявки, и сводка используют Java-класс `OverduePolicy`.

## Ограничения

- Аутентификации нет: в задании её не было.
- Категории только из миграции, без создания и удаления.
- Учебный стенд преподавателя не выдан. Pipeline на `main` собирает образ, запускает его и проверяет health, создание заявки, смену статуса и сводку. Внешний SSH-деплой включается секретами `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_PATH`. Локально ту же проверку делают `scripts/deploy-local.ps1` и `scripts/rollback.ps1`.
- Откат — это запуск предыдущего образа по тегу коммита. Миграции практики только добавляют объекты: `V3` добавляет nullable-столбец `change_comment`, старое приложение его не читает.
- Секреты в репозиторий не кладутся. Пароль в Compose по умолчанию — учебный `support`, для стенда его заменяют через `.env`.

## Как показать на защите

1. Открыть критерий «закрытую заявку нельзя вернуть в работу» в спецификации, метод `TicketService.changeStatus` и тест `forbiddenOperationDoesNotChangeStoredData`.
2. Через Swagger или `http/support-api.http` создать заявку, перевести её в `IN_PROGRESS`, затем в `RESOLVED`, запросить сводку.
3. Показать `ReportController` на Java и `ReportService` на Kotlin.
4. Повторить переход `RESOLVED → IN_PROGRESS` и получить HTTP 409 без изменения истории.
5. Показать workflow `.github/workflows/ci.yml`: на pull request нет публикации, после `main` образ проверяется запуском. Откат — `scripts/rollback.ps1 -Tag <sha>` или workflow `Rollback`.
6. Для сбоя базы, health check и миграции использовать раздел диагностики в README.
